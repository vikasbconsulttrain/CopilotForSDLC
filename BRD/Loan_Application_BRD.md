# Business Requirements Document (BRD)

# Loan Application and Credit Assessment System

**Document Version:** 1.0
**Business Domain:** Retail Banking
**Application:** Loan Application Platform
**Document Status:** Approved for Development Analysis

---

## 1. Business Objective

The bank intends to introduce a digital Loan Application and Credit Assessment platform that allows customers to apply for personal loans through a digital channel.

The platform should capture customer and employment information, validate the application, perform credit assessment, determine eligibility, and provide an initial loan decision.

The system should reduce manual processing, improve consistency in credit assessment, provide faster decisions to customers, and maintain an auditable record of the application and decision-making process.

The initial release will support Personal Loans.

---

## 2. Scope

### 2.1 In Scope

The solution will support:

* Customer registration and identification
* Creation of a loan application
* Capture of personal information
* Capture of employment and income information
* Capture of requested loan amount and tenure
* Validation of application information
* Credit score retrieval
* Credit eligibility assessment
* Debt-to-income assessment
* Additional credit verification for higher-value loans
* Loan decision generation
* Application status tracking
* Application history
* Basic audit information
* Notifications related to application status

### 2.2 Out of Scope

The following are not included in the initial release:

* Final loan disbursement
* Collection and repayment processing
* Credit card applications
* Mortgage loans
* Vehicle loans
* Manual underwriting workstation
* Customer relationship management functionality

---

## 3. User Roles

The system will support the following users.

### 3.1 Customer

A customer can:

* Start a loan application
* Enter personal information
* Enter employment and income information
* Specify the requested loan amount and tenure
* Submit an application
* View application status
* View the reason for rejection where applicable

### 3.2 Loan Officer

A loan officer can:

* Search loan applications
* View application details
* View credit assessment results
* View validation failures
* View the decision generated by the system
* Request additional verification for an application

### 3.3 Credit Analyst

A credit analyst can:

* Review credit information
* Review risk indicators
* Review applications requiring additional verification
* Record an additional verification result
* Approve or reject an application requiring manual verification

### 3.4 System Administrator

An administrator can:

* Manage configurable loan rules
* Manage application status values
* View audit information
* Manage notification configuration

---

## 4. Loan Application Process

The expected high-level process is:

1. Customer starts a new loan application.
2. Customer provides personal information.
3. Customer provides employment and income information.
4. Customer specifies loan amount and tenure.
5. System validates the application.
6. System retrieves the customer's credit score.
7. System evaluates credit eligibility.
8. System evaluates income and debt-related criteria.
9. If additional verification is required, the application is routed for additional credit verification.
10. System generates an initial loan decision.
11. Customer is notified of the application result.
12. Application and decision information are stored for future reference.

---

## 5. Customer Information Requirements

The application must capture the following customer information:

* Customer ID
* Full name
* Date of birth
* Email address
* Mobile number
* Residential address
* PAN or equivalent tax identifier
* Existing customer indicator

Customer ID must be unique.

The system should validate that mandatory customer information has been provided before allowing the application to proceed.

The customer must be at least 21 years old to apply for the personal loan.

The customer's mobile number and email address must follow valid formats.

The tax identifier must follow the bank's configured validation rules.

---

## 6. Employment and Income Information

The customer must provide:

* Employment type
* Employer name
* Employment start date
* Monthly gross income
* Monthly net income
* Existing monthly loan obligations
* Other recurring financial obligations

Supported employment types initially include:

* Salaried
* Self-employed
* Professional

Monthly net income must be greater than zero.

The system must reject an application when monthly income is zero or negative.

Existing monthly obligations cannot be negative.

The system should calculate the customer's debt-to-income ratio using the configured calculation rule.

---

## 7. Loan Request

The customer must specify:

* Requested loan amount
* Loan tenure
* Purpose of loan

The initial supported loan amount is between ₹10,000 and ₹2,000,000.

The initial supported loan tenure is between 6 and 84 months.

The system must reject applications outside the configured amount or tenure limits.

The loan amount must be greater than zero.

---

## 8. Credit Assessment

After successful application validation, the system must retrieve the customer's credit score from an external Credit Bureau service.

The credit bureau integration is expected to provide:

* Customer identifier
* Credit score
* Number of active loans
* Total outstanding balance
* Number of recent credit enquiries
* Credit report reference

The system must retain the credit report reference but should not store the complete credit report unless explicitly required by the bank's data retention policy.

If the credit bureau service is unavailable, the application should not be automatically approved.

The application should be placed into a `Credit Check Pending` state and the customer should be informed that processing is delayed.

---

## 9. Credit Eligibility Rules

The following initial rules apply.

### Rule 1 - Minimum Credit Score

Applications with a credit score below 650 should normally be rejected.

Applications with a credit score of 650 or above can proceed to the next assessment stage.

### Rule 2 - Credit Score Boundary

A credit score exactly equal to 700 must be treated as a valid score and must not be incorrectly classified as either below or above the threshold.

### Rule 3 - Debt-to-Income Ratio

The customer's debt-to-income ratio should be calculated as:

Existing Monthly Obligations / Monthly Net Income

The configured maximum debt-to-income ratio is 45%.

Applications exceeding the configured ratio should be rejected unless they qualify for an additional review process.

### Rule 4 - Loan Amount Threshold

Applications with a requested loan amount greater than ₹25,000 require an additional credit verification.

An application for exactly ₹25,000 does not require the additional verification solely because of the loan amount.

### Rule 5 - High-Value Application

For applications above ₹25,000:

* Additional credit verification must be initiated.
* The application cannot receive a final approval until the additional verification is completed.
* The verification result must be recorded against the application.

---

## 10. Additional Credit Verification

Additional verification may be performed by a Credit Analyst.

The Credit Analyst must be able to:

* View the application
* View customer information
* View income information
* View credit score
* View calculated debt-to-income ratio
* Record verification comments
* Mark verification as Passed or Failed

If additional verification fails, the application must be rejected.

If additional verification passes, the application can continue to the final decision stage.

The system must maintain an audit record of who performed the verification and when it was performed.

---

## 11. Loan Decision

The system can generate one of the following initial decisions:

* Approved
* Rejected
* Credit Check Pending
* Additional Verification Required

The decision must include:

* Application ID
* Decision
* Decision date/time
* Credit score used
* Debt-to-income ratio
* Verification status where applicable
* Decision reason

A rejected application must contain a reason.

The system should not expose internal scoring details or sensitive risk information directly to the customer.

---

## 12. Application Status

The application may move through the following statuses:

```text
Draft
Submitted
Validation Failed
Credit Check Pending
Credit Assessment
Additional Verification Required
Approved
Rejected
```

The system must prevent invalid status transitions.

For example, an application in `Rejected` status cannot move back to `Approved` without an explicitly authorized administrative process.

---

## 13. Notifications

The system should notify customers when:

* An application is successfully submitted
* Additional information is required
* Credit verification is pending
* Additional verification is required
* The application is approved
* The application is rejected

Notifications may initially be sent through email and SMS.

Notification failures should be logged but should not automatically change the loan application decision.

---

## 14. Application Search and Tracking

Loan officers must be able to search applications using:

* Application ID
* Customer ID
* Customer name
* Mobile number
* Application status
* Submission date

Search results should display:

* Application ID
* Customer name
* Requested amount
* Submission date
* Current status
* Decision where available

A loan officer should be able to open an application and view its complete processing history.

---

## 15. Audit Requirements

The system must maintain an audit trail for significant activities.

Audit events should include:

* Application creation
* Application submission
* Changes to customer information
* Changes to loan information
* Credit score retrieval
* Credit assessment
* Additional verification
* Decision generation
* Status changes
* Administrative rule changes

Each audit event should contain:

* Event ID
* Application ID
* User/system responsible
* Event type
* Event timestamp
* Previous value where applicable
* New value where applicable

Audit records must not be editable by normal application users.

---

## 16. Integration Requirements

The solution will initially integrate with the following external services.

### 16.1 Credit Bureau

The Credit Bureau service will provide credit information.

The integration should support:

* Request/response processing
* Timeout handling
* Service-unavailable handling
* Invalid response handling
* Correlation/reference ID tracking

### 16.2 Notification Service

The application will use a notification service for email and SMS.

The system should support retrying transient notification failures.

A permanent notification failure should be logged.

### 16.3 Customer Information Service

Where the applicant is an existing bank customer, the system should be able to retrieve basic customer information from the Customer Information Service.

If the customer cannot be found, the application should not silently create a duplicate customer record.

---

## 17. Validation and Exception Scenarios

The system must handle the following scenarios:

* Missing customer information
* Invalid customer identifier
* Customer below minimum age
* Invalid email address
* Invalid mobile number
* Missing employment information
* Zero income
* Negative income
* Negative existing obligations
* Loan amount below minimum
* Loan amount above maximum
* Loan tenure outside supported range
* Credit score unavailable
* Credit bureau timeout
* Credit bureau returns an invalid response
* Customer not found in customer information service
* Customer information service timeout
* Duplicate application submission
* Notification service failure
* Unauthorized attempt to change application status

The system should provide meaningful error messages without exposing internal system details.

---

## 18. Security Requirements

The application must enforce role-based access.

Customers must only be able to access their own applications.

Loan Officers must only access applications permitted by their assigned branch or business unit.

Credit Analysts must have access to applications requiring credit verification.

Administrative functions must require appropriate authorization.

Sensitive customer information must not be written to application logs.

Authentication and authorization failures must be logged.

The application must protect against common web application security vulnerabilities including:

* Injection
* Broken access control
* Sensitive data exposure
* Improper input validation
* Cross-site scripting
* Insecure direct object references

---

## 19. Non-Functional Requirements

### Performance

Normal application validation should complete within 3 seconds excluding external service response time.

Application search should normally return results within 3 seconds.

### Availability

The application should target 99.9% availability during agreed business operating periods.

### Scalability

The system should support at least:

* 500 concurrent users
* 10,000 applications per day

The architecture should allow capacity to be increased without major application redesign.

### Reliability

External service failures should not cause application data corruption.

Requests should use correlation IDs to support troubleshooting across services.

### Observability

The system should provide:

* Application logs
* Error logs
* Integration logs
* Correlation IDs
* Application metrics
* External service response metrics

---

## 20. Data Retention

Loan application information must be retained according to the bank's applicable data retention policy.

Credit bureau information must follow applicable contractual and regulatory retention requirements.

Audit information must be retained for the period defined by the bank's compliance policy.

Expired information must be archived or deleted according to approved retention rules.

## 22. Acceptance Expectations

The first release will be considered functionally complete when:

* A customer can submit a valid personal loan application.
* Mandatory information is validated.
* Invalid applications are rejected with appropriate validation messages.
* Credit information can be retrieved from the Credit Bureau.
* Credit eligibility rules are applied consistently.
* Applications above ₹25,000 are routed for additional verification.
* Applications at exactly ₹25,000 are not routed solely because of the amount threshold.
* Credit verification failures are handled appropriately.
* Approved and rejected decisions contain the required information.
* Customers can track their application status.
* Loan Officers and Credit Analysts can perform their permitted activities.
* Significant activities are auditable.
* External integration failures are handled without corrupting application data.
* Security and authorization requirements are enforced.
